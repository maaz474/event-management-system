Mohammed MaazPRN 202456111997

Abstract

  • Introduction: The Event Management System (EMS) is a web application that lets a college or club publish events and lets students register for them online.
  • Problem addressed: Events are usually announced on notice boards and WhatsApp groups, and registrations are collected on paper or in spreadsheets. This causes confusion, duplicate entries and no live view of seats.
  • Proposed solution: One system where an administrator creates and manages events, students log in, browse and register, and reports are generated automatically.
  • Technologies used: HTML5, CSS3 and JavaScript (ES6) with browser Web Storage as the database; GitHub for version control; VS Code as the IDE.
  • Expected outcomes: Faster registration, no overbooking, accurate attendee lists and instant reports that can be exported as CSV.

2. Problem Statement

Background

Colleges, clubs and departments organise seminars, workshops, technical contests and cultural programmes throughout the year. Each event needs publicity, registration, seat control and a final attendee list.

Existing issue

Information is scattered across posters, WhatsApp messages and paper forms. Organisers cannot tell how many seats are left, students register twice or miss deadlines, and compiling reports takes hours.

Need for the proposed system

A single, easy-to-use system is needed that shows every event in one place, controls capacity automatically, keeps accurate records and produces reports on demand.

3. Existing System

Current process

  1. The organiser prepares a poster or message with event details.
  2. The notice is pinned on boards or forwarded in groups.
  3. Students write their names on a sheet or fill a shared form.
  4. The organiser counts entries by hand before the event.

Existing technologies

Paper registers, notice boards, WhatsApp groups, Google Forms and Excel sheets.

Working mechanism

Data flows one way, from the organiser to students, through informal channels. Registrations are collected separately and merged manually, so no part of the process is connected.

4. Limitations of Existing System

  • Manual process: every step depends on people copying data.
  • Time-consuming: counting, sorting and verifying lists takes hours.
  • Data redundancy: the same student appears in several lists.
  • Human errors: spelling mistakes, lost sheets and wrong counts.
  • Security issues: personal details are shared openly in groups.
  • Poor scalability: the process breaks down when events or students increase.
  • No real-time seat status: overbooking is common.

5. Proposed Solution

Objectives

  • Provide one place to publish and browse events.
  • Allow online registration with automatic seat control.
  • Give administrators full control over events and attendees.
  • Generate summary and attendee reports instantly.

Features

  • Registration and login with two roles: Admin and Student.
  • Create, update and delete events (title, date, time, venue, category, capacity, description).
  • Search and filter by category; live seat bar on every event.
  • One-tap register and cancel; duplicate and overbooking checks.
  • Dashboard of totals and fill rate; CSV export; mobile-friendly interface.

Working methodology

The user opens the web page, logs in, and the interface changes according to the role. All actions go through JavaScript service functions that validate the input, update the data store and refresh the screen.

Benefits

Less paperwork, correct attendee counts, quick reports, and access from any phone or computer without installing anything.

7. Non-Functional Requirements

These describe how the system should perform.

  • Performance: pages respond in under one second for up to a few thousand records.
  • Security: passwords are stored as hashes, never as plain text; admin functions are hidden from students; all user input is escaped before display.
  • Reliability: data stays saved between visits; invalid input is rejected with a clear message.
  • Availability: works offline once the file is on the device.
  • Maintainability: code is split into small, named functions and is commented.
  • Scalability: the storage layer can be swapped for a server database without changing the interface.
  • Usability: large touch targets, readable text, and a layout that adapts to phones, tablets and desktops.

8. Software Development Life Cycle (SDLC) Model Used

Selected model: Agile (iterative, sprint-based).

Why this model was selected

  • The team is small and requirements became clearer as screens were demonstrated.
  • Working software was needed early so features could be tested on real phones.
  • Changes such as extra fields or report types had to be absorbed cheaply.

Advantages

  • Early and continuous delivery of working features.
  • Easy to accept requirement changes.
  • Frequent testing reduces defects.
  • Good communication between team members.

10. System Architecture

The system uses a three-layer design that runs entirely in the browser.

Presentation layerHTML + CSS user interface, responsive for phones
Login / RegisterEvent list & formsMy registrationsReports
▼ user actions  |  ▲ updated screens
Application (logic) layerJavaScript services with validation and role checks
AuthServiceEventServiceRegistrationServiceReportService
▼ read / write JSON  |  ▲ records
Data layerBrowser Web Storage (key: ems_db)
userseventsregistrations

Data flow

The user acts on the interface; the interface calls a service; the service validates the request and updates the stored JSON; the interface is redrawn from the new data.

Communication between modules

Modules communicate through plain function calls with simple objects, so the data layer can later be replaced by REST calls to a server without changing the screens.

13. Testing Strategy

Types of testing

  • Unit testing: each function (hash, validate event, seatsLeft) tested on its own.
  • Integration testing: login → register → cancel flow across modules.
  • System testing: whole application on phone and desktop browsers.
  • Acceptance testing: students and a staff coordinator try real scenarios.

16. Advantages

  • Saves time for organisers and students.
  • Reduces manual work and paper.
  • Improves accuracy with automatic seat and duplicate checks.
  • Easy to maintain – plain HTML, CSS and JavaScript.
  • Secure – role-based access and hashed passwords.
  • Scalable – storage can be replaced by a server database.
  • User-friendly – works on any phone without installation.

17. Future Enhancements

  • Native mobile application.
  • Cloud deployment with a shared database so data syncs across devices.
  • Real-time notifications and email / SMS reminders.
  • QR-code tickets and attendance scanning at the venue.
  • Analytics dashboard with charts.
  • AI-based event recommendations.
  • Multi-language support.

18. Conclusion

Objectives achieved: the Event Management System lets administrators publish and manage events and lets students register and cancel online, with automatic seat control and one-tap reports.

Benefits: it replaces scattered notices and paper lists with one reliable system, cutting effort and errors.

Overall impact: event organisation becomes faster, more transparent and easier to audit.

Future scope: moving to a cloud database, adding notifications, QR check-in and analytics will turn the prototype into a full campus platform.
